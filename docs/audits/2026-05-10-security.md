## High Severity

---

### H-1 — Bundled xmrig binary: ad-hoc signed only, no upstream hash verification

**Location:** `BurnCycle/BurnCycle/Resources/xmrig`, `build.sh`

**Issue:** The bundled `xmrig` Mach-O (arm64, 7.0 MB, SHA-256: `c66f9881bed79a550e18d54b9ae5cf03b91a0e881efdbf7962db2e58de0b4f7b`) carries only an ad-hoc (self) signature (`flags=0x20002(adhoc,linker-signed)`, `TeamIdentifier=not set`). It is not signed by Apple, not notarized, and bears no Apple Developer identity. `build.sh` copies it verbatim with no SHA-256 check at build time. There is no documented provenance — the README does not state which xmrig release version or release tag this binary was built from, nor which build pipeline produced it.

**Risk:** Any developer-workstation or supply-chain compromise that replaces the binary goes undetected. The binary runs with the full privileges of the parent app (unsandboxed, see H-2), has outbound network access to the mining pool, and executes OpenCL on the GPU. A trojanized binary could exfiltrate data, install persistence, or mine to an attacker's wallet.

**Recommendation:**
1. Document the exact xmrig release tag and upstream binary URL in `README.md` and a `Resources/xmrig.sha256` file.
2. Add a SHA-256 verification step in `build.sh` before the `cp` and `chmod +x`.
3. Obtain or build the binary with a valid Apple Developer signature (requires Developer ID Application certificate) so Gatekeeper can verify it independently.
4. At runtime in `MiningManager.start()`, verify the SHA-256 of `xmrigPath` before `proc.run()` and abort if it does not match the expected value.

### H-2 — No app sandbox; xmrig inherits unrestricted process privileges

**Location:** `BurnCycle/BurnCycle/Info.plist`

**Issue:** `Info.plist` contains no `com.apple.security.app-sandbox` entitlement (value absent entirely). The app is not sandboxed. xmrig is launched via `Process()` and inherits the parent's full user-level permissions, file-system access, and environment (including any secrets present in `ProcessInfo.processInfo.environment`). There is no `com.apple.security.temporary-exception.*` or hardened-runtime entitlement set.

**Risk:** A compromised or malicious xmrig binary can read any file accessible to the user, write to arbitrary locations (e.g., `~/Library/LaunchAgents` for persistence), and make arbitrary outbound connections beyond the declared mining pool.

**Recommendation:** Enable the hardened runtime (`com.apple.security.hardened-runtime`) and add the minimum required entitlements. If sandboxing is incompatible with xmrig process spawning, document the explicit threat-model decision and apply process isolation: spawn xmrig under a dedicated low-privilege helper with a restricted environment (cleared `env`, explicit `PATH` only).

### H-3 — No code signing or notarization; Gatekeeper will block distribution

**Location:** `build.sh` (lines 7–22)

**Issue:** `build.sh` performs `swift build -c release` and copies the product and xmrig into an `.app` bundle but does **not** run `codesign` or `xcrun notarytool`. The resulting `.app` will be quarantined by Gatekeeper on any target Mac where it was not locally built. Users who download or copy the `.app` will see a "cannot be opened because the developer cannot be verified" error and must manually bypass Gatekeeper.

**Risk:** Users are trained to bypass Gatekeeper for this app, normalizing insecure behavior. The app also bundles an unsigned third-party binary (xmrig), which macOS 13+ Gatekeeper is increasingly aggressive about blocking even inside a signed app unless each bundled executable is individually signed.

**Recommendation:** Add `codesign --deep --force --options runtime --sign "Developer ID Application: ..."` and `xcrun notarytool submit` steps to `build.sh`. Each bundled executable (xmrig) must be individually signed before the app bundle is signed.

## Medium Severity

---

### M-1 — Hardcoded developer XMR wallet address as default

**Location:** `MiningManager.swift` line 14

**Issue:** The string `4AAzgq4qzFaBfdvx5ZkDgeUAi51T4AbDibjSKcpMCSJz1e8ipp4X3eDaPLE2nuobeJXkFEJPF5YFWAxoDsLJNrMU8xyBLVV` is the hardcoded default wallet address (`private static let defaultWallet`). It is passed as a plain `--user` argument to xmrig and will appear in plaintext in the compiled binary, in the xmrig log at `$TMPDIR/burn_cycle_xmrig.log`, in the process argument list visible via `ps aux`, and in any crash reports. Users who never visit Settings will mine to this address indefinitely without realizing it.

**Risk:** The README footnotes this as intentional ("supports development"), but the disclosure is easy to miss. Users who believe they are not mining or believe mining is disabled may still send compute resources to the developer's wallet. This is a transparency and consent issue, not just a technical one.

**Recommendation:** On first launch (or whenever the wallet field is empty), present an explicit opt-in dialog explaining that the default wallet belongs to the developer. Persist the user's explicit choice. Add a visible indicator in the UI when the developer default wallet is active.

---

### M-2 — xmrig pool connection: TLS enabled but no certificate pinning

**Location:** `MiningManager.swift` lines 43–51

**Issue:** The pool is `xmr-us-east1.nanopool.org:14433` with `--tls` passed to xmrig. TLS encrypts the transport but xmrig performs standard TLS certificate validation against system roots — there is no pinning. A network-level adversary with a trusted CA cert (corporate MITM proxy, compromised CA) can intercept the pool connection, observe the wallet address, redirect hashrate to an attacker-controlled pool, or inject malicious stratum responses.

**Recommendation:** Pass `--tls-fingerprint <sha256-of-pool-cert>` to xmrig, or document the accepted risk. Alternatively, allow users to configure a self-hosted or pinned pool endpoint.

---

### M-3 — xmrig log at predictable world-readable tmp path; log may capture wallet address

**Location:** `MiningManager.swift` lines 12, 52

**Issue:** The log file path is `NSTemporaryDirectory() + "burn_cycle_xmrig.log"` — a fixed, predictable path with no randomization. On macOS, `NSTemporaryDirectory()` is user-specific (`/var/folders/.../T/`) but the filename is constant. Any process running as the same user can race to open or replace this file (symlink attack / TOCTOU). Additionally, xmrig's startup output typically echoes the `--user` wallet address into the log file, meaning the wallet address is written in plaintext to disk.

**Recommendation:** Use `FileManager.default.temporaryDirectory.appendingPathComponent(UUID().uuidString + "-xmrig.log")` to generate a non-predictable path per session. Set restrictive permissions (`0600`) on the file immediately after creation before passing it to xmrig.

### M-4 — Shortcut name passed unsanitized to `shortcuts run`; argument injection via newlines

**Location:** `ChargingController.swift` lines 104–105

**Issue:** `process.arguments = ["run", name]` where `name` is the user-supplied shortcut name from `AppSettings` (stored in `UserDefaults`). Using an argument array (not a shell string) is safe against shell injection, so this is **not** a shell-injection issue. However, if `name` contains a newline character or null byte, `/usr/bin/shortcuts` may behave unexpectedly (log pollution, argument truncation). No sanitization or validation is applied to `name` before use.

**Recommendation:** Validate `shortcutName` in `AppSettings` or `ChargingController.runShortcut` to ensure it contains only printable non-control characters. Reject or strip newlines, null bytes, and leading/trailing whitespace.

---

### M-5 — `unsafeFlags(["-lIOReport"])` in Package.swift suppresses Swift 6 safety checks

**Location:** `BurnCycle/Package.swift` line 13

**Issue:** `linkerSettings: [.unsafeFlags(["-lIOReport"])]` disables Swift Package Manager's build safety checks for the affected target. `IOReport` is a private Apple framework with no public API guarantees. Using `unsafeFlags` also prevents this package from being used as a dependency by any other package, and the use of a private framework means the app may silently break on any macOS update.

**Recommendation:** Document the specific IOReport symbols used and add a fallback code path for when the framework is unavailable. If `IOReport` is only needed for GPU % monitoring, consider whether the degraded fallback (zero GPU %) is acceptable, making the private link optional.

## Low Severity

---

### L-1 — xmrig inherits full parent process environment

**Location:** `MiningManager.swift` line 40 (`let proc = Process()`)

**Issue:** `Process()` without setting `proc.environment` inherits the full environment of the parent app, including any secrets that macOS or shells may inject (e.g., `SSH_AUTH_SOCK`, `AWS_SECRET_ACCESS_KEY`, tokens set by login items or shell profiles). xmrig does not use these but could log them on crash.

**Recommendation:** Set `proc.environment = ["PATH": "/usr/local/bin:/usr/bin:/bin"]` (or the minimum required for xmrig) to prevent environment leakage to the child process.

---

### L-2 — `lastError` in `ChargingController` may surface raw stderr from `shortcuts`

**Location:** `ChargingController.swift` lines 142–146, 171

**Issue:** Raw stderr from `/usr/bin/shortcuts` is captured and assigned to `self.lastError`, which is displayed in the UI. If `shortcuts` ever emits sensitive system information (HomeKit token fragments, user credentials, CoAP session tokens) in its error output, this surfaces in the UI and may be logged by the app.

**Recommendation:** Sanitize or truncate `errMsg` before display. Consider stripping anything that looks like a token (long hex/base64 strings). Cap the displayed message length.

---

### L-3 — No update mechanism; bundled xmrig will not receive security patches

**Location:** `build.sh`, `README.md`

**Issue:** The app has no auto-update mechanism and the bundled xmrig binary is a static artifact checked into the repository. When xmrig publishes security fixes (e.g., memory-safety fixes in the OpenCL or TLS code), this binary will not be updated unless the developer manually replaces it. Users have no way of knowing their xmrig version is outdated.

**Recommendation:** Add a `XMRIG_VERSION` constant to `MiningManager.swift` and display it in the Info panel. Document the update process in `README.md`. Consider a periodic check against the xmrig GitHub releases API to alert users of available updates.

---

### L-4 — `system_profiler` subprocess output not size-limited; potential memory exhaustion

**Location:** `BatteryMonitor.swift` lines 195–196

**Issue:** `pipe.fileHandleForReading.readDataToEndOfFile()` reads the entire `system_profiler SPPowerDataType` output into memory without a size bound. On a normal system this is ~3–10 KB, but if the output is unexpectedly large (future macOS changes, system anomaly), it could briefly allocate significant memory.

**Recommendation:** Read up to a reasonable maximum (e.g., 64 KB) and discard the rest, or use a streaming line-by-line reader that stops after finding the target field.

---

### L-5 — `refreshHealthDetail` error from `proc.run()` silently swallowed

**Location:** `BatteryMonitor.swift` line 193

**Issue:** `try? proc.run()` discards any launch error. If `/usr/sbin/system_profiler` is unavailable or fails to launch, `healthPercent` silently remains at its last value with no user-visible indication. This can lead to stale health data being displayed.

**Recommendation:** Capture the error and set a flag (e.g., `healthReadFailed: Bool`) that the UI can display as "Health unavailable."

---

### L-6 — README discloses developer wallet address and encourages default use

**Location:** `README.md` line 89

**Issue:** The README documents that when the Wallet field is left empty, mining proceeds to "the developer's wallet" to "support development." While not a secret, the disclosure is a single table-cell footnote that most users will not read. This is a consent and transparency gap.

**Recommendation:** Add a dedicated "Privacy & Mining" section to `README.md` that explicitly describes: (a) what data leaves the device (wallet address, hashrate to pool), (b) who benefits from default-wallet mining, and (c) how to opt out. Mirror this information in an in-app disclosure.
